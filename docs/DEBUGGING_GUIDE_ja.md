# FPGA 開発デバッグガイド

ハードウェアのデバッグは、ソフトウェアのデバッグとは異なるマインドセットが必要です。好きな場所で一時停止したり、簡単にコンソールにログを出力したりすることはできません。このガイドでは、設計を効果的にデバッグするためのツールとテクニックを紹介します。

## 1. シミュレーション (Verilator)

**「まずはシミュレーション、実機はその後」**
これが鉄則です。ハードウェアでのデバッグは時間がかかり、内部状態もほとんど見えません。シミュレーションなら、すべての信号をナノ秒単位で確認できます。

### テストの実行

このプロジェクトでは、`make test` コマンドを使って、Verilator で SystemVerilog コードをコンパイル・実行します。

```bash
make test
```

### 波形の確認 (GTKWave)

テストが失敗した場合や、内部の挙動を確認したい場合：

1. `make test` を実行して `.vcd` (Value Change Dump) ファイルを生成します。
2. GTKWave でファイルを開きます：

    ```bash
    gtkwave tb_alu_4bit.vcd  # ファイル名は例
    ```

### 波形の見方

- **クロックエッジ:** `clk` が 0 から 1 に変わる垂直な線（立ち上がりエッジ）を探します。ここで `always_ff` の更新が行われます。
- **リセット前の状態:** 最初（時刻 0）の時点では、信号が `x`（不定/赤色）やランダムな値になっていることがあります。リセット信号 (`rst_n`) がこれらを正しく 0 に初期化しているか確認しましょう。
- **遅延 (Latency):** 順序回路の出力は、クロックエッジの**後**に更新されることを忘れないでください。入力がクロックエッジの瞬間に変化した場合、レジスタの出力はその少し後（シミュレーションステップ上）に変化します。

## 2. ハードウェアデバッグ

シミュレーションが通ったら、実機（FPGA）に移ります。ここで動かない場合は、以下のテクニックを使います。

### 💡 「Lチカ」デバッグ

ボード上の LED は一番の友達です。

- **ステータス表示:** 内部フラグ（例：`Zero Flag`、`State == WAIT`）を LED に割り当てて光らせます。
- **ハートビート:** クロックが動いているか、FPGA が正しく書き込まれているかを証明するために、常に 1 つの LED を（カウンタを使って）点滅させておきます。

### 🖥️ LCD デバッグ（ハードウェア版 printf）

Day 04 以降では、LCD コントローラを構築します。これは事実上の「標準出力」になります。

- **Info 命令 (`IFO`):** Day 18 では、レジスタの値を画面にダンプするカスタム命令を実装します。
- **メモリの可視化:** 特定のメモリ領域を画面にマップすることで、データの変化をリアルタイムで監視できます。

### 🛑 クロックを遅くする

6502 CPU のロジックは複雑です。27MHz で動かすと、LED では何が起きているか全く見えません。

- **クロック分周:** LCD/HDMI のクロックは高速なまま維持し、CPU ロジック用のクロック有効信号（Enable）を 1Hz や 10Hz に落とします。こうすることで、命令の実行フローを LED や LCD 上でステップごとに確認できます。

## 3. よくある問題チェックリスト

### シミュレーションは通るのに、実機で動かない？

1. **リセット論理:**
    - リセット信号は `active low` (`rst_n`) ですか、`active high` (`rst`) ですか？
    - ボードのリセットボタンを押しましたか？
2. **クロックの安定性:**
    - クロックピンの割り当ては正しいですか？
    - PLL の設定は正しいですか？
3. **入力のフローティング:**
    - `.cst` ファイルですべての入力ボタンに `PULL_MODE=UP/DOWN` を設定しましたか？入力が浮いていると、動作が不安定になります。
4. **タイミング違反:**
    - （上級編）レジスタ間のロジックが複雑すぎると、1 クロックサイクル以内に計算が終わらないことがあります。合成レポートに "Timing Constraints" などの警告が出ていないか確認しましょう。

### 「ロジックの挙動がおかしい」

1. **ラッチの生成:** `always_comb` ブロック内で、`else` や `default` ケースを書き忘れていませんか？
2. **ビット幅の不一致:** 4ビットの値を3ビットの配線に代入していませんか？（例：`logic [2:0] x = 4'b1111;` -> `x` は `111` になってしまいます）。
3. **感度リスト:** 古い Verilog の `always @(a)` は、`b` が変化したときに更新されないバグを生みがちです。SystemVerilog の `always_comb` はこれを自動的に解決します。**常に `always_comb` を使いましょう！**
