# よくある落とし穴 (Common Pitfalls)

ソフトウェアエンジニアが FPGA (SystemVerilog) を学ぶ際に、直感と異なりハマりやすいポイントをまとめました。

---

🌐 Available languages:
[English](./COMMON_PITFALLS.md) | [日本語](./COMMON_PITFALLS_ja.md)

## 1. 「`=`」と「`<=`」の使い分け (代入のタイミング)

これが最大のハマりポイントです。

- **Software**: `a = 1; b = a;` と書けば、`b` は必ず `1` になります（上から順に実行される）。
- **Hardware**: 順序回路 (`always_ff`) で `a <= 1; b <= a;` と書くと、**`b` には「更新前の `a` の値」が入ります**（すべて同時に更新される）。

FPGA の順序回路では、クロックの立ち上がりの瞬間に、すべてのレジスタが一斉に値を更新します。`<=` (ノンブロッキング代入) は「次の瞬間の値」を予約するもので、即座には書き換わりません。

詳しくは [SystemVerilog チートシート](./SYSTEMVERILOG_CHEATSHEET_ja.md) を参照してください。

## 2. チャタリング (ボタン入力の罠)

- **Software**: `if (keyPressed)` は 1 回だけ反応すると思いがちです。
- **Hardware**: 物理的なボタンは、押した瞬間に電極がバウンドして「ON/OFF/ON/OFF...」と高速に切り替わります（チャタリング現象）。

これをそのまま `always_ff @(posedge button)` のクロックに入れたり、カウンタのイネーブル信号にすると、**1 回押しただけで数十回反応する** という現象が起きます。
これを防ぐには「デバウンス (Debounce)」という回路 (数ミリ秒待ってから値を確定させるフィルタ) が必要になります。

## 3. "Printf" デバッグができない

- **Software**: わからなくなったら `console.log` や `printf` を仕込んで変数の値を見ます。
- **Hardware**: FPGA 内部にコンソールはありません。

**どうすればいい？**

1. **シミュレーション**: `make test` で動くテストベンチ内なら `$display()` が使えます。これが基本です。
2. **実機**: LED に信号を出力して光らせるか、Day 04 で作るような「LCD 表示回路」を使って画面に値を出す必要があります。

## 4. 未初期化変数の振る舞い (X: 不定値)

- **Software**: 変数は通常 0 や null で初期化されるか、コンパイルエラーになります。
- **Hardware**: シミュレーションでは、初期化していないレジスタは「**X (不定)**」という状態になります。

`X` に `1` を足しても `X` のままです。リセット信号 (`rst_n`) を正しく使って、システムの起動時にすべてのレジスタを `0` などの確定値にすることが非常に重要です。
なお、実機では `X` という状態はなく、たまたま `0` か `1` になります。これが「シミュレーションと実機の挙動が違う」原因の一つです。

## 5. 暗黙のラッチ生成

- **Software**: `if (flag) val = 1;` と書いたとき、`flag` が false なら何もしないのが当たり前です。
- **Hardware**: 組み合わせ回路 (`always_comb`) でこれをやると、「`flag` が false のときは**以前の値を保持する**」という記憶回路 (ラッチ) が勝手に作られてしまいます。これは意図しないタイミングエラーの原因になります。

**解決策**: `always_comb` では、`if` に必ず `else` をつけるか、冒頭でデフォルト値を代入 (`val = 0;`) して、**どのような経路でも必ず値が決まる**ようにしてください。
