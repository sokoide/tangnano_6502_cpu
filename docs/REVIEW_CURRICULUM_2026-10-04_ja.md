レビュー対象: HEAD `975b42c`。ルート、Day01–18 starter/completed、Day99 の日本語 README と関連 RTL / Makefile / ROM / testbench を静的に照合。本日の変更は `425cc86..975b42c` を参照。シミュレーション、合成、配置配線、実機確認は今回未実施。以下の RTL 指摘はソース上の条件と状態遷移に基づく。

## 優先して修正する項目

### 1. Day03 の分周器が説明どおり動かない

- 根拠: `day03_completed/clock_divider.sv:22` と `day03_completed/README_ja.md:45`。
- `div_ratio=2` は counter=0 で threshold=1 未満、counter=1 で周期末の分岐に入り、どちらも clk_out=0。周期的な出力を生成しない。4 でも counter=2 のときだけ High になり、定常デューティは 25%。1 も常時 Low。
- 修正案: 支持する分周比と High/Low の長さを先に定義する。奇数分周のデューティと ratio=0/1 の扱いも定義し、それに合わせて RTL と README を修正する。既存 make test の交通信号テストはこの分周器の保証にならない。

### 2. Day02 のスターターでFPGAビルドを完結できない

- 根拠: `day02/Makefile:20` は `hw_20k.gprj`、24 行は `hw_9k.gprj` を要求するが、どちらもない。starter にはボード用 top / CST もない。
- README は top.sv の編集や実機への ALU 統合を指示するが、completed の top_9k.sv / top_20k.sv は点滅回路だけで ALU を接続しない。LED 点滅では ALU を確認できない。
- 修正案: ALU の必須課題をシミュレーションと明示し、点滅は completed を使った書込み確認と区別する。ALU の実機統合を必須にするなら、その配線・入力・観測方法とビルドファイルを用意する。

### 3. Day05–17 の表示書込みFSMが未同期VSyncを参照する

- 根拠例: `day05_completed/lcd_demo.sv:157`、`day17_completed/lcd_demo.sv:259`。LCD_CLK 領域の vsync を MEMORY_CLK / cpu_clk の always_ff から直接読む。starter 側にも同じ構造がある。
- VRAM 読出しと font 読出しを LCD_CLK へ揃えた修正だけでは、この制御信号の CDC は解消しない。メタステーブル状態やイベント検出の不確実性が残る。今回、実機での障害発生は確認していない。
- 修正案: Day18 の vsync_meta / vsync_cpu のような同期化を適用する。1 フレームに 1 回の更新を意図するなら、同期後の立上りを検出する。Day10–17 の boot 開始も PLL LOCK 待ちを持たないため、Day18 の起動制御と合わせて見直す。

### 4. Day18 の WVS #0 の説明とRTLが違う

- 根拠: `day18/README_ja.md:54` は N 回待つと記載。一方 `day18_completed/cpu.sv:96` は VSync イベントが来て初めて count<=1 を判定するため、0 でも 1 回待つ。
- 現行動作は max(1,N) 回。Day99 の N+1 回との差にも 0 の例外がある。現行 Day18 テストの #2 では検出できない。
- 修正案: 現行 RTL を保つなら 0 の動作を明記。N 回仕様を採るなら 0 を即時完了にする。教材の継続性を優先するなら Day99 との統一も検討し、ROM オペランドとテストの期待値を一緒に合わせる。

## READMEの正確性と学習導線

### 5. Day06 / Day07 の実装手順がスターターと一致しない

- `day06/README_ja.md:17`: pc_enable を追加する指示だが、`day06/cpu.sv:10` に既にある。
- `day07/README_ja.md:98`: always_comb へのデコード追加を指示するが、現行 CPU は always_ff 内の case(data_in)で処理する。X/Y と debug_x/debug_y も既に宣言済み。
- 修正案: 既存の枠組みと学習者が埋める TODO を分け、状態名と挿入先を直接示す。Day08 も独立 ALU を統合する説明ではなく、現行の CPU 内演算とフラグ更新に合わせる。

### 6. ルートの実機手順が完成例を書き込む

- `README_ja.md:75` は学習者が dayXX を編集・テストした後、dayXX_completed の download を例示する。その操作では学習者の実装を実機確認できない。
- 修正案: ビルド可能なスターターでは `make -C dayXX download BOARD=9k` を主手順にし、completed は回答例の確認用と説明。Day01–03 の不足するビルド環境は別途説明する。
- カリキュラム表の Day05「NOP」も現行の到達点（opcode を解読せず PC を進める）に合わせる。各 Day は独立した starter であり、前日の編集が自動的に次 Day へ反映されないことも記載する。

### 7. RAM容量に1KiBの計算違いがある

- `day10/README_ja.md:27` と completed は $0200–$7FFF = $7E00 バイトを 30.5KB と記載。正しくは 32,256 バイト = 31.5KiB。
- Day99 の $0200–$7BFF は 31,232 バイト = 30.5KiB で正しい。Day10 と Day99 の領域差を保って修正する。

### 8. Day17の実装クロック数と標準6502サイクルが混在する

- `day17/README_ja.md:68` の「1 命令で 5～6 サイクル」は標準 6502 の参考値であり、現行の複数 FSM 状態と memory_ready 待ちを含む実装クロック数ではない。
- Day08 / 10 / 11 / 12 / 13 / 14 / 17 の表も標準値である旨を揃える。Day15/16 の説明を共通化できる。
- Day17 の図は JMP $1000 ではなく JMP ($1000)。また RTL はポインタ上位バイトを 16bit で+1 して読むため、NMOS6502 の JMP ページ境界バグを再現しないことをこの Day にも明示する。
- 分岐式の PC が opcode 番地なのか operand 番地なのかも明示する。Day09 の現行 FSM では operand 処理時の PC から+1 する。

### 9. Day08のフラグ定義に境界値の誤りがある

- `day08/README_ja.md:51`: 符号付き 8bit 範囲は -128～127。「±127 を超えた」では-128 を誤って overflow と扱う。
- C の「255 を超えた」は ADC の説明。SBC の C はボローなしを示す。後段の説明と統合する。
- 二進演算を実装すること、decimal 演算が対象外であることも「完全に実行」の代わりに明示する。

### 10. Day03→04とDay04内の到達点が矛盾する

- `day03/README_ja.md:289` は翌日に CPU レジスタとフラグを実装すると説明するが、Day04 は LCD 接続課題。
- Day04 冒頭は CPU 命令・レジスタ表示が今日のゴールとする一方、後半では CPU 未接続と説明する。
- Day04 のメモリ表は現行 Day10–18 に適用されず、Day99 の mirror も反映しない「予定の配置」。現在の配線と将来の紹介を最初から区別し、VRAM のポート内アドレス `row*60+column` を主に教える。

- 各 Day の先頭に「今日編集する箇所」「実装済みの前提」「テストの期待値」「実機 ROM の期待値」を短く置く。Day05/06 の到達点形式を全 Day へ展開する。

- DEX/DEY 追加テストは通常値、ゼロ、wrap を検査している。C/V の保持は現在 0 のままなので、C=1/V=1 の事前条件も与えると誤ったクリアを検出できる。実機 ROM が DEX/DEY を使わない点は必須の不具合ではないが、実機でこの課題を観測する例はあるとよい。
- Day99 README の相対リンクではない `docs/...`、クローン URL のプレースホルダー、Go/srecord 等の前提条件を整理する。日本語 README 内のローカル Markdown リンクは静的確認で欠落を検出しなかった。
