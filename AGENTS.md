# Repository Guidelines

## Project Structure & Module Organization

- `dayXX/` contains the starter workspace for each lesson (edit SystemVerilog here).
- `dayXX_completed/` contains reference solutions and build tooling for each day.
- `docs/` holds SystemVerilog cheatsheets, debugging guides, and prerequisites.
- Testbenches typically live alongside sources and are named `tb_*.sv` (with generated `*.vcd` waveforms).

## Build, Test, and Development Commands

- `make` or `make build`: build all `day*_completed` projects for the selected board.
- `make test`: run simulations across completed days (Verilator-based).
- `make clean`: clean build artifacts for all completed days.
- `make format`: run `markdownlint` on docs and `verible-verilog-format` on `.sv`/`.svh` files.
- `make BOARD=20k`: set the target board (default is `9k`).
- Per-day build/program (completed days): `make -C dayXX_completed` and `make -C dayXX_completed download`.

## Coding Style & Naming Conventions

- SystemVerilog is the primary language; keep indentation at 4 spaces and line length to ~100 columns (matches `verible-verilog-format`).
- Testbenches use the `tb_*.sv` naming pattern; waveform outputs are `*.vcd` for GTKwave.
- Keep day folders aligned with the curriculum (`day01`, `day01_completed`, etc.).

## Testing Guidelines

- Use Verilator simulations via `make test` or a per-day `sim` target where available.
- Inspect waveforms with GTKwave when debugging (`*.vcd` files are already generated by many testbenches).
- When adding a module, provide or update a `tb_*.sv` that exercises both nominal and edge cases.

## Commit & Pull Request Guidelines

- Commit messages follow short prefixes such as `add:`, `fix:`, `update:`, `improve:`, `refactor:`, or `lint`.
- Keep PRs focused; include a brief summary, affected day(s), and any relevant screenshots or waveform snippets when behavior changes.

## Tools, Prereqs, and Configuration

- FPGA builds rely on GOWIN tools; see `docs/PREREQS.md` for installation.
- You may need to set `GWSH` and `PRG` paths for local toolchain discovery.
